# Tier-2 integration map and verification (2026-11-04, second pass)

Scope: SOS issues #13, #14, #19, #20 and tracker #9. This file records which
Tier-2 capability backs each SOS feature, how the SOS side behaves when the
capability fails, and the verification evidence.

SOS calls only `https://synapsedx.sbs` (`@synapsedx/capabilities`). It never
imports `@synapseone/sdk`, never calls SynapseOne, and never touches a Tier-1
port, queue or database.

## Capability map

## #14 — EOP draft generated by Tier-2 AI

- `POST /v1/emergency/eop/generate-draft` builds a prompt from the emergency
  event (id, code, type, severity, location, impact, opaque asset ids), the
  linked hazards, the resource inventory and `additional_context`, calls the
  Tier-2 AI chat capability, and validates the JSON answer
  (`objectives`, `actions`, `operational_phases`, `assignment_matrix`,
  evacuation/fallback/communications plans).
- Missing sections are filled from the event-specific doctrine, but a payload
  with no objectives or no usable actions is rejected (`502 ai_draft_invalid`)
  instead of being padded.
- Provenance: `metadata.generated_by = "tier2-ai"`, `ai_provider`,
  `model`, `prompt_version = "sos-eop-prompt-v1"`, `usage`, `generated_at`,
  `source_refs`, `capability_gaps`.
- `force_new_version` is serialised per event (`withLock`) so version selection
  and creation cannot race; exactly one plan per `(event, version)`.
- Deterministic draft is only produced on explicit opt-in
  (`{"fallback":"deterministic"}`), is labelled `deterministic-fallback` with
  `ai_error`, and keeps the same version/id rules. Hazard deploy uses the
  labelled fallback so an AI outage cannot block incident creation.
- Tests: `eop.test.ts` (prompt payload, payload mapping, rejection),
  `contracts.test.ts` (201 AI draft with provenance, idempotent replay,
  forced version 2 then 3 with only one v1, 503 with no persisted plan,
  explicit fallback, 502 on invalid JSON), `ai.test.ts` (content/JSON
  extraction, typed 503, caching).

## #13 — VNDMS ingestion, SOS side

- `POST /v1/hazards/ingest` (authenticated, `emergency:dispatch`) validates a
  batch (max 2000), normalises coordinates/warning type/level, upserts by
  stable `hazard_id`, and records a run in `sos-hazard-ingest-runs`.
- `GET /v1/hazards/ingest/status` combines the latest push run with the Tier-2
  scheduled connector: job id/name/kind, schedule, enabled, last run,
  last success, run count, and an error code. Absence of a job is
  `connector.configured = false`; the overall status is `unconfigured` when
  neither a push run nor a connector exists.
- SOS contains no scheduler, cron, poller or local queue.
- Tests: `vndms.test.ts` (job match, run projection, combined freshness,
  unavailable API) and `contracts.test.ts` (status from fake Tier-2 jobs,
  degraded on failed run, disabled connector, jobs API outage).

## #19 — SDK, public projection, event transport

- Public projections already read `datasets.entities`; the contract test now
  proves a record with `published: false` never appears and that an entity API
  failure returns `502` instead of reading private records.
- SSE consumes the Tier-2 event feed with a cursor and honours
  `Last-Event-ID`; the old unconditional 30 s list poll now only runs when the
  feed is unavailable.
- The console filters terminal statuses client-side as well and uses a shared
  `emergencyStatusLabel`, so a cached payload never labels a resolved/canceled
  event "Đang triển khai".
- SDK: SOS installs `@synapsedx/capabilities@^0.3.0` from the public npm
  registry. No sibling checkout, vendored tarball or prebuild is used.

## #20 — idempotency, ETag, metrics, timeouts, binary proxy

- Reads expose `ETag: "<record version>"` and `x-record-version`; updates send
  `If-Match` (or accept `if_version`) and return `409 record_version_conflict`
  on a stale version. `If-Match`/`if_version` disagreement is `400`
  `version_precondition_mismatch`; a non-numeric `If-Match` is `400`.
- Deploy returns the existing event/plan when `linked_event_id` is set, and a
  concurrent link update resolves to the same deterministic ids. Approval is a
  no-op when the same unit is already assigned (no second write).
- `write()` retries only a `409` create conflict, conditionally on the version
  it just read; a `400` is surfaced.
- Gateway forwards `If-Match`, `If-None-Match`, `Last-Event-ID` upstream and
  returns `ETag`/`x-record-version`/`x-sos-scan-truncated`/`Retry-After` to the
  client; timeouts return `504`; console bytes are proxied binary-safely and
  `HEAD` has no body.
- Metrics: request RED, Tier-2 call result/latency, `sos_tier2_conflicts_total`,
  `sos_eop_draft_total{source}`, `sos_hazard_stream_total{transport}`.
